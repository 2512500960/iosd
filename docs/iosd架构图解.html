iosd 文件结构与运行机制

这份说明先介绍 iosd 的文件构成、初始化组织和执行设施，再通过 CDP、CLI 配置生成和 EHSA 说明业务代码怎样协作。函数地址作为回到 IDA 复核的入口，跟随对应职责一起给出。

适用对象为 C8000v IOS XE 26.01.02，MD5 9eccfd46caadfff9c18557e2a446e19b。图分为两类：关系示意解释概念，样本局部实现只画已有证据支持的连接。实线和虚线按图例标注调用、登记、数据读取或待确认边界。

1 文件到底大在哪里

本轮在不访问 IDA 的情况下重新读取原始 ELF 头、program headers 和 section headers，并对整个文件校验 MD5、SHA256。文件长度为 938,319,552 字节，约 894.85 MiB。图按 ELF 标志统计各类内容占用的文件字节数。

文件部分 大小 阅读时应该想到什么
带执行标志的节 643.80 MiB，约 71.9% 机器码及跳板等可执行内容，包含已观察到的执行变体
已分配的只读数据节 178.26 MiB，约 19.9% 常量、重定位表、展开信息及相关只读内容
已分配的可写数据节 68.94 MiB，约 7.7% 初始化数据、指针槽和注册元数据等
未分配元数据及其他文件空间 约 3.85 MiB 文件元数据、节头和对齐空间；装载范围由 PT_LOAD 描述

两个很大的可执行节分别是 .text（约 311.40 MiB）和 CRPGC_text0（约 331.81 MiB）。本轮复用的 BGP 函数证据中，普通消息处理函数 EFCCF10 有 simulation 条件分支，转入 22AD4E30；后者位于 CRPGC_text0。这个实例将普通处理入口与 simulation 条件分支联系起来。两个节中其余函数的用途和对应关系继续按具体入口分析。

只读部分也值得拆开：.rela.dyn 约 76.10 MiB，.eh_frame 约 45.25 MiB，.rodata 约 42.15 MiB。其中重定位表保存装载相关信息，展开信息服务于栈展开，.rodata 则保存各类只读常量。

文件共 8,906 个节，其中 8,866 个名字以 .btrace 开头，这些节总共约 5.54 MiB。大量细分节来自这组诊断相关命名，业务功能的组织则通过初始化记录、登记接口和实际处理代码继续定位。

还要分清文件和内存：.bss 声明约 211.22 MiB，CRFT_func 声明约 7.42 MiB，二者都是 NOBITS，大小由节头描述，装载时按其内存语义处理。3 个 PT_LOAD 的 p_memsz 合计约 1,109.64 MiB，包含运行时零初始化区域；RSS 由运行时驻留页面决定；进程还会使用堆、线程栈和外部共享库。core 读取按实际捕获的页面范围进行。

新测量还有一个很实用的对比：subsystem 描述符区只有 546,432 字节，module header 为 480 字节，module link 为 264 字节。不到 0.6 MiB 的导航元数据就能提供大量初始化入口。先读懂这些入口，比按地址顺序逐个看几百 MiB 的机器码有效。

布局摘要与适用范围见 原始 ELF 布局。这些数值描述当前样本的容器结构，组件职责由后文的关系和消费代码说明。

2 文件 初始化 执行与业务关系

可以把 iosd 同时看作四张相互连接的图。

文件与进程图回答代码放在哪里。主 ELF、.so 是装载容器，进程是运行地址空间。Linux 线程可以执行同一进程里不同文件中的代码。主 ELF 可以调用库函数，库中的事件循环也可以在同一地址空间回调主 ELF。

初始化图回答功能怎样准备好。subsystem 记录给出名字、类别、init 和属性；module header/link 给出另一套分组、依赖和回调关系。init 的具体工作包括状态准备、队列创建、回调登记或任务创建，各项工作沿其调用和参数逐条确定。

执行与连接图回答工作怎样发生。registry 保存可供其他代码查找的功能入口；队列保存尚待处理的工作或报文；task、线程和事件循环提供执行上下文。登记函数和实际调用函数的代码可能相距很远，普通直接调用图不一定把它们连起来。

业务与状态图回答用户真正关心的行为。命令改变配置状态，报文改变协议运行状态，定时器和平台消息也会改变状态；NVGEN 从相关状态生成配置文本。共享对象、锁、回调和上下文决定这些路径怎样交会。

一个函数可同时拥有几个不同的描述：“机器码在 iosd 主 ELF”“作为 CDP 的回调登记”“由某个队列消费者调用”。这些关系共同说明函数的位置、接入方式和执行来源。分析记录保存输入、条件、消费者和状态，用于继续追踪具体行为。

3 启动时怎样把功能准备好

当前样本的 ELF 入口是 B2463A0。它通过 libc 启动设施进入 main 包装器 B246530，再将应用回调交给运行时代理。应用回调 B2464A0 的相应成功分支进入系统初始化 D7B7690。图中的代理边界表示回调传递；代理内部的调度细节列为后续核对范围。

在已审查的系统初始化路径中，先准备执行环境，然后准备 module 发现容器、发现记录、整理初始化关系，再推进相关类别和分组。这个顺序解释了“线程先存在，后面的功能再把工作接入”的一种实际组织方式。

subsystem 描述符的已保存目录中有 5,692 条记录，分为 13 个类别，包括 Kernel、Library、Driver、Protocol、Management、Registry、SystemInit、EHSA 等。类别作为初始化编排属性使用，实际顺序由相关顺序表和调用路径决定。Kernel 类别组织 IOS 内部的基础设施。Protocol 类别有 2,016 条候选记录，Registry 有 1,731 条，这些数值统计候选初始化记录。

module 机制另有 15 条 header：14 个 level_* 分组和带回调的 memtest。11 条已保存 link 中，10 条是前置依赖，1 条把 memtest 归入 level_protocol 分组。这里可以确认这个 module 内部的成员关系；没有同样的证据把所有 Protocol 类别的 subsystem 塞进该分组。

E0E33E0 的相关路径既推进 Protocol 类别，又推进 level_protocol 分组，说明两套机制在启动中协作。两套记录分别参与发现、分类、依赖处理和回调执行。

深入的消费者、布局及依赖例子见 模块与子系统；ELF 入口、代理与应用回调见 启动与术语。这些初始化关系由静态代码和保存记录支持，启动时的实际执行顺序可结合运行轨迹继续核对。

4 登记接口与输入处理

图展示登记、查找、回调和队列消费之间的一种常见连接方式；各协议的具体路径在对应实现中展开。

初始化时，代码把 callback 放进 registry 的某个键或槽。运行时，分发者依据输入种类查这个键，再调用当时绑定的 callback。它可能马上处理输入，也可能把输入入队，让另一个消费者稍后处理。想证明“报文到达了这里”，需要把写入端和消费端接起来。

因此，从 init 出发要同时看直接调用和“把代码地址作为参数传进去”的地方。从字段解析函数反向追，则要检查谁提供缓冲区、长度、接口或邻居上下文，以及经过了哪些拒绝条件。普通 xref 没有连起来也不代表实现不存在：tagged 大端指针、动态槽和未分析代码都可能造成缺边。

分析中记录以下状态及各自的证据范围：

状态 直接证据 继续关联的内容
静态定义存在 文件/IDB 中有描述符或实现候选 运行时登记记录
当前登记存在 某次暂停快照里槽或链表指向它 配置和上下文门控
条件放行 已核对的特定门控满足 路径中其余条件
实际执行 有对应运行轨迹或执行证据 该次状态、平台和输入范围

CLI 的晚注册、帮助显示和解析门控分别保存。协议回调按其实际职责标注，例如收包、清理、接口变化或认证查询。

5 用 CDP 把抽象关系接到真实代码

CDP 的已复核初始化入口 CD878F0 通过相关路径使 CD894C0 创建名为 CDP Protocol 的 IOS 内部 task，入口为 CD89F00。task 入口创建 CDP packets 队列，并登记键 65、回调 CD8AB90。这里的 65 是登记接口使用的键，含义由该接口的登记和消费路径确定。

CD8AB90 检查接口及启用状态、队列容量。相应成功分支把报文交给队列，拒绝分支另有释放或通用处理。CD89F00 的事件循环从同一队列取包，继续检查上下文，再调用 CD8AF90。

CD8AF90 检查最小头长、版本、校验和以及 TLV 边界，查找或分配邻居记录，进入缓存更新路径并设置 TTL 相关计时。部分扩展项和后处理还通过 registry 回调处理，尚未全部枚举。

这条链带来两个具体结论：第一，已审查的头/TLV 与邻居处理实现在主 ELF 内；第二，入队成功和完成协议解析是两个阶段。设备报文入口如何经平台设施进入这套回调，以及所有外部边界，仍需补齐。

对比 BGP 和 OSPF 可以看出，不应该把 CDP 结构写成所有协议的模板：BGP 已找到消息分发和会话状态门控，但 TCP 字节流到消息的组装仍有缺口；OSPF 已找到队列消费者与 LS Update 分支，但认证、区域选择到队列的前半段还未闭合。UDP 的 socket 查找与投递又是另一种连接方式。

本轮恢复 MCP 后，还补了三段具体证据。OSPF 的 FC2A190 在普通参数路径根据 IP 头长度计算后续头位置，读取 +1 字节，并把不在已检查范围的类型转为 0；它的调用者 FBE9060 才按返回值将类型 4 交给 FC05800。因此“取类型”和“处理 LS Update”是相邻但不同的职责。

BGP 的 F20A5E0 已核对大小失败、缓冲准备、属性处理调用、NLRI 长度核算及后续分支。属性处理目标 F1F8D10 有 57,547 字节，超过本批 16,384 字节的反编译上限；该调用及失败分支有证据，目标内部的全部属性处理仍未恢复。后续属性类型及各分支的处理继续从这些入口展开。

UDP 的投递路径还有一个具体的分工：CE451D0 的一条分支调用 CE44F10，但继续读后者可见，它仍会检查广播资格、入队，并可能通过 registry 通知下游。应用层载荷处理入口继续沿这组队列和通知的消费端定位。

完整的局部证据及 LLDP、IS-IS 等未完成入口见 协议处理链 和 定位索引。

6 配置是一条输入路径，也有一条生成路径

输入 hostname ... 时，parser 沿语法图匹配关键字和参数，准备 parser context（CSB），再调用 handler 修改状态。以后显示 running-config 时，NVGEN 使用生成上下文及配置语法/对象迭代路径，让相应回调读取状态并输出文本。

在已核对的 hostname 案例中，CLI EOL 与 NVGEN 节点都指向 handler E0E6A00，selector 均为 0；handler 根据 NVGEN 标志走不同分支。接口 description 也有共享回调的实例，接口对象中保存描述状态。输入分支负责校验和更新状态，生成分支负责读取状态和输出配置文本。

生成引擎 E0DE210 负责上下文和调度；nvgens_action 的消费者 E39D8F0 把生成调用接到业务回调；公共输出封装经 E0D9CD0 → E0D8B20 → E0E1B20 汇总文本。框架可以不理解每个协议的具体配置字段，组件回调负责解释自己的状态。

接口配置文本缓存是生成路径的一个优化：符合资格且命中缓存时复用文本，否则生成并在相关路径保存。已经定位开关、资格、命中、保存和部分清理路径；当前是否启用、哪些接口有缓存、所有失效触发器并未全部验证。图中保留缓存资格和命中条件。

show running-config 给出生成的配置文本，ICM 组织相应配置内容，parser 图保存命令定义和语法关系。配置状态、命令定义、当前登记和生成文本分别记录。详见 NVGEN 与接口缓存。

7 线程 任务 队列与函数调用

Linux pthread 是操作系统调度的执行实体。IOS 内部 task 则是 iosd 内部调度设施管理的工作上下文。队列保存待处理对象，函数是被调用的代码入口。task、pthread 和 subsystem 的关联由创建者、调度设施及实际消费路径确定。

此前现场的线程调查核对了 IOS 主线程、Fastpath、Packet、Auxiliary、Sim Aux 和两个 worker。主 ELF 调用执行环境准备设施；部分 pthread 的创建和事件循环实际在 libiosd_crb_vxe_unix.so 内，worker 的实际绑定在 libthpool.so。这些绑定对应已记录的现场，其他会话按当时映射继续核对。

Auxiliary 是一个有用的跨文件例子：库中的循环等待请求，调用主 ELF 的出队接口取得函数指针，再执行请求。循环在 so，队列接口和业务回调可以在主 ELF。分析时分别记录线程循环、队列接口、业务回调及最终绑定的文件位置。

CDP Protocol、EHSA peer monitor、REDUNDANCY FSM 等名字出现在内部 task 的创建证据中；没有证据把它们一一分配给 IDA 列出的 Linux 线程。实际归属需要现场栈、调度器映射或请求消费证据。

level 也要随消费者解释：module 的 level_protocol 是分组名字；thread_level 相关代码建立栈/执行上下文；CLI privilege 是另一套访问属性。文档按各自的消费者和取值范围解释这些名字与字段。细节见 线程、任务与 level。

8 EHSA 展示协议之外的状态驱动协作

EHSA 的局部实现把“发现对端失联”和“完成主备切换”分成多个阶段。类型 30 的 KEEPALIVE 接收经过 D51E0E0 分派到登记回调 D512810，相应路径刷新监测。peer monitor D510B80 负责周期活动及超时相关分支。

失联产生的 raw event 7 经过 D50F450 的过滤和平台策略，必要时提交 FSM 事件队列。FSM task D519FC0 再经 D51A800 使用通用表驱动引擎推进状态。raw event 7、网络消息类型 30 和 FSM 的 major/minor 属于不同编号空间。

平台 init D52C3A0 在能力条件成立时安装有关回调；其中 D52D8D0 的相关路径访问 Chasfs，发布 notification/stby-request-swo 属性。此前对部分实际绑定的核对指向 libchasfs.so，但属性发布后的外部消费者和完整切换结果仍没有闭合。

心跳发送、超时检测、FSM 投递、平台请求和切换完成分别对应一段处理及观测证据。详见 EHSA 实现。

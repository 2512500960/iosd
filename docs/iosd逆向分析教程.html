iosd 程序架构与分析指南

系统边界 初始化机制 功能注册与运行时验证

iosd 的规模来自大量业务功能、公共设施、注册元数据与运行时对象共同组成的程序。理解它需要先分清文件和进程边界，再沿启动编排、subsystem、module 分组及注册接口进入具体功能。CLI 是其中一种入口，消息、协议报文和数据模型同样需要单独分析。

本文围绕当前 C8000v 26.01.02 样本说明已有代码证据支持的架构关系，并保留地址、结构和复现方法作为查阅材料。输入 MD5 为 9eccfd46caadfff9c18557e2a446e19b，使用 IDA 9.1；项目浏览入口已更新至 0.6.1。旧静态材料的 imagebase 为 0，文中相应样本地址按 RVA 理解，rebase 后加当前基址；堆 VA 不能照此换算。

导读 结构与阅读路径

整体架构可从第1、3、4、10部分连贯阅读；地址表示见第2部分；CLI 注册与条件见第5至9部分。VPDN 是注册和状态依赖的具体案例，不代表其完整网络协议解析路径。插件、调试与结果使用方式放在后半部分。

这里使用三种说法标记结论的强度：

标记 含义 例子
已核对 现有字节、消费代码或保存的路径直接支持该局部关系 某 EOL 描述符包含一个 handler 指针
候选 有具体线索，但身份、控制流或运行条件还有缺口 一个 handler 可能通过间接调用提交某张表

“已核对”也有范围。确认代码中存在一个调用，并不等于确认这个调用在设备上执行过。每个结论都要带着它的对象、输入身份和成立条件来读。

文中“示意”用于解释结构或算法，“样本案例”对应实际保存的分析结果。出现 <string>、<number>、<cr> 的文字是语法模板，不是让你原样输入设备的操作指令。

1 系统边界与组织方式

1.1 IOS XE 与 iosd

可以把 IOS XE 理解为一个包含 Linux 和多个用户态程序的系统。iosd 是其中承载大量 IOS 控制面功能的程序；研究这一份 iosd 文件，可以看到很多命令解析、配置处理、协议和平台控制相关代码。

但 iosd 文件并不包含整个设备的全部实现。已有资料中还出现 pman、cmand、fman_rp、fman_fp、confd、nginx、wsman、vtyc 等进程或组件名称。某次功能操作可能经过多个边界，也可能只在 iosd 内部完成。名称和进程关系要在对应平台、版本中核对。

IOS XE 系统
├─ Linux 与进程管理设施
├─ iosd
│  ├─ CLI 解析与配置相关代码
│  ├─ 协议和平台相关代码
│  └─ 消息、注册、调度等公共设施
└─ 其他用户态进程与服务
   └─ 与 iosd 的关系要沿实际接口分析

因此，“分析 iosd 的结构”至少包含两种工作：一是整理文件里面的代码和元数据；二是理解它与运行时对象、其他进程和设备状态的联系。

1.2 这些名词不在同一层

名词 比较容易理解的含义 它不能直接告诉你的事
进程 正在运行的一份程序及其地址空间 一个进程内部只有一个功能模块
线程 操作系统调度的执行实体之一 一个 subsystem 必须对应一条线程
子系统 subsystem 带名称、初始化入口和属性的注册实体 这个实体拥有一段连续、独占的全部代码
module header/link 编译或初始化组织留下的元数据 一定是“子系统下面的业务模块”
component 源码组织中的组件标签 与运行时 subsystem 一一对应
编译单元 编译源文件时形成的组织单位 看到一个 .c 路径就恢复了该单元的全部函数
函数 一段可调用代码 这个函数只处理一个命令或一种消息
handler 在某个分派场景中被调用的处理函数 名称含 handler 就一定是 CLI handler

“模块”在口语里容易同时指源码目录、ELF 元数据、共享库、功能组或子系统。阅读报告时，最好说清楚“module header 记录”“源码 component”或“某个子系统”，不要全叫模块。

1.3 为什么它不像一棵文件夹目录树

一个公共函数可以被多个协议调用；一个注册中心可以服务多个子系统；同一 CLI handler 可以处理多个 selector；多个语法路径还可以共享一个终结点。

所以，最终更合理的表示是关系图：

源码路径 ──直接引用线索──→ 函数
子系统记录 ──初始化入口──→ 函数
语法终结点 ──处理函数──→ 同一个函数
消息分派表 ──消息回调──→ 另一个函数

每条边只表达一种关系。不要因为两条边都指向某函数，就把它们合成“这就是这个子系统全部代码”的结论。

1.4 从上到下理解程序

可以按“系统环境 → ELF 与共享库边界 → 启动编排 → 初始化实体 → 注册接口 → 业务处理路径”阅读。各层回答的问题不同：文件视角定位实现在哪里；启动视角解释何时准备；subsystem 和 module 元数据提供组织线索；接口与回调连接输入和业务处理。

iosd 主 ELF 与外部文件、进程的边界
  → 启动入口及初始化阶段
    ├─ subsystem 类别、实体及 init
    └─ module 分组、依赖及回调节点
      → CLI / 消息 / registry / 协议入口
        → 缓冲区解析、状态对象、定时器及后续调用

这条阅读路径不表示所有对象都有唯一父级。公共 registry、调度和消息设施会被多个实体使用。当前还没有恢复所有功能的报文处理路径，也没有完整的跨库归属；名称、直接调用、注册、分派和数据流应作为不同关系保存。

从已有实现可归纳出元数据驱动初始化、分阶段准备、注册与间接分派连接功能等特点。这里说明的是样本呈现的组织方式，不将推断写成厂商的设计意图。

2 地址与内存表示

2.1 先理解字段偏移

假设一个记录从地址 0x1000 开始，文档说“名称指针在 +24”。它的意思是：名称指针这个字段存放在 0x1018，因为十进制 24 等于十六进制 0x18。

你还需要读取该字段，才得到名称字符串所在地址。下面三个对象要分开：

记录地址         0x1000
名称指针字段地址 0x1000 + 24 = 0x1018
字段中保存的值   例如 0x5000，指向字符串

“槽地址”和“槽里的指针”也是这个区别。把槽地址直接当成节点地址，会从错误的位置开始解释结构。

2.2 文件偏移不是内存地址

文件偏移表示字节在磁盘文件中的位置。VA 表示虚拟地址空间中的位置。ELF 的装载描述决定文件中的哪些字节映射到哪些地址；不能默认二者相等。

IDB 或 .i64 是 IDA 的分析数据库，包含反汇编、名称、交叉引用和分析状态。它也不等于原始 ELF。运行时内存中还会出现文件里没有直接存放的堆对象和初始化结果。

2.3 EA RVA 与运行时 VA

用一张表记住四个量：

量 含义
旧 EA 当时静态报告中的 IDA 地址
旧基址 这次报告采集时的 imagebase
RVA 对同一映像基准的相对位置：旧 EA - 旧基址
当前 EA / 运行时 VA 分别把 RVA 加到当前 IDB 基址或运行时同一映像基址

例如，这是一个示意基址，不是当前设备的真实值：

旧基址 = 0
旧 EA  = 0x00123400
RVA    = 0x00123400

新 IDB 基址 = 0x70000000
当前 EA     = 0x70123400

运行时基址 = 0x70000000
运行时 VA  = 0x70123400

IDA 已经移到运行时位置时，EA 与 VA 可以相等。再加一次 0x70000000 就错了。

另一个方向也成立：IDA 可以保持旧基址，运行时另有加载基址。此时必须通过 RVA 转换，不能直接把静态 EA 交给 debugger 读取。

2.4 堆地址为什么不能照样换算

模块内的全局变量通常可以用模块 RVA 标识。某个变量里保存的指针，却可能指向动态分配的堆节点。堆节点的位置不由静态映像中的一个固定偏移决定。

因此，应当先定位全局槽，再读槽中的运行时指针，再按布局读堆节点。不能把“堆 VA 减去 iosd 基址”得到的整数随意称为有效映像 RVA。

2.5 大端 小端与 tagged pointer

字节序描述多字节数值怎样存放。用数字 0x12345678 举例：

大端：12 34 56 78
小端：78 56 34 12

本样本的静态 CLI 数据里有小端指针，同时某些编号用大端保存；运行时又可以出现带标记位的大端指针。因此不能对整个文件统一 byteswap。

tagged pointer 是在指针表示中附带标记。下面是结构示意：

原始字节：80 00 00 00 00 12 34 56
按大端读：0x8000000000123456
清最高标记位：0x0000000000123456

若先按小端装载，得到的是 0x5634120000000080。此时标记位在原始整数中的位置已经不同。源码里先掩码再 byteswap 的写法，也可能正确，但掩码必须与这种表示配对。不能把两个看起来相似的掩码互换。

插件提供 little、big、mask_then_swap、swap_then_mask 四种解码选项。它们是四种明确的解释方式，不是四个任选其一、总会正确的开关。应当以消费代码和已知对象核对。

2.6 原始数值与逻辑数值

VPDN 的 selector 28 按大端保存时，字节可以是 00 00 00 1C。在某些小端装载的反编译表达式中，这会表现成 0x1C000000，十进制是 469,762,048。

因此，看到很大的比较常量，先检查字节序。它可能只是逻辑编号 28 的存储表示，也可能确实是一个大标志值；解释必须结合读取方式。

3 子系统与模块元数据

3.1 四种组织视角

第一种是文件和装载布局：代码、只读数据、可写数据、导入表等。第二种是初始化元数据：subsystem、module header 和 link。第三种是源码路径与保留名称。第四种是实际调用、引用和数据流。

这四种视角互相补充。例如，名称提示某函数属于许可功能，源码路径又提供了 component 标签；但只有进一步检查调用和引用，才能知道它参与哪个具体流程。

ELF 的 section、装载用 program segment 和 IDA 显示的 segment 也要区分。名称相似不代表它们逐项对应。

3.2 子系统记录

当前样本保存的扫描结果有 5,692 条子系统候选、5,678 个不同名称。消费代码支持按 96 字节步长处理相关子系统记录。插件扫描还使用双 magic 定位候选，再尝试读取名称和初始化入口。

这两句话分别说明“消费代码的步长”和“扫描器的定位方法”。扫描器不应仅因预想记录大小，就跳过所有不符合预想对齐的区域。

元数据可以告诉你某个实体的名称和 init 入口，但不能自动给出它所有函数的地址区间。把 init 入口往外扩一大段当成模块边界，可能把公共函数和其他实体混进去。

3.3 module header 与 link

module 与 subsystem 是两套初始化组织机制。当前 32 字节的 module header 共 15 条：14 个 level_* 分组和一个带回调的 memtest。24 字节 module link 共 11 条，其中 10 条表达前置依赖，1 条把 memtest 放入 level_protocol 分组。这些关系来自新核对的消费者，不能把 module 分组当作 subsystem 的父目录。

sub_D772690 根据 header 的 +0x10 是否非零，分别建立带回调节点或含列表的分组节点；sub_D7715A0 调用前者的初始化回调。level_* 的相应字段均为零；memtest 的第一回调为 RVA 0xD79CF90。第二回调的完整消费尚未核对，保留原始字段，不直接命名为退出或析构函数。

原始 link tag 小端值 0xDFEADFEA 由 sub_D7705B0 处理，将端点 B 加入端点 A 的前置依赖列表。0xABEFABEF 由 sub_D7703A0 处理，将 A 的分组设为 B。例如 level_protocol 依赖 level_driver，而 memtest 归入 level_protocol。依赖边与分组边表达不同事实。

subsystem 则读取自己的类别和属性，由 sub_D710240、sub_D710BC0 等组织分类及依赖。启动的后续路径中存在 sub_D711090(4) 与初始化 level_protocol module 分组相继执行的例子；这是启动编排的配合，不能据此断言所有 Protocol subsystem 都是该 module 的子节点。

模块还可能指功能集合，或主 ELF/共享库这样的文件容器。文件归属、初始化归属和业务关联必须分开记录。完整结构、设计解释与原始函数证据见 iosd 模块 子系统与初始化架构。

3.4 源码路径能帮到什么程度

已有样本中可以找到这类路径：

../VIEW_ROOT/cisco.comp/parser/src/parser_chunk_malloc.c
../VIEW_ROOT/cisco.comp/fnf/config/model/field_spec/src/fnf_cm_field_spec.c

它们可以帮助识别 parser、fnf 等源码组织标签。当前扫描取得过 3,542 条路径线索。

但一个函数引用某个路径，可能是日志、断言或共享辅助代码。合理记录方式是“这个函数直接引用该路径字符串”，再把组件归属记为候选，而不是声称已恢复完整编译单元。

3.5 符号和日志的使用方法

_message_handler、mqipc_*、tbl_*、__be_*、vty_* 等名称可以分类检索。IDA 名称还可能是以前人工添加的；sub_XXXX 中的数字通常反映地址，不是跨构建稳定的语义名称。

日志里的 __func__ 字符串可以提供更好的函数名线索。例如日志格式含函数名参数和行号参数时，应当恢复实际参数值，再核对调用位置。只看见格式串附近一个名字，不能保证它就是引用函数的名字。

.btrace_*、GUID、计数器和追踪 ID 则是另一类证据。它们有助于关联诊断设施，但没有自动变成源码函数名。CRFT_func 的精确运行时布局仍未确认。

4 启动与初始化架构

4.1 从入口到应用代码

本样本已核对的局部启动关系是：

ELF start
  → 从 main 指针槽取得函数地址
  → libc 调用 main 包装器
  → 包装器把应用回调交给运行时代理
  → 应用回调执行环境准备
  → 进入系统初始化路径

“指针槽叫 main”和“某函数就是 main”不是同一个判断。当前真正的 main 包装器对应旧地址 0xB246530；旧文档把 0xD710460 称为 main，已被后续复核纠正。

运行时代理接收回调，不等于代理内部所有调度过程都已经分析完。画图时应保留“传入回调”这种边的含义，不能伪装成一条已确认的普通直接调用。

4.2 子系统准备与执行初始化

子系统准备阶段会建立分类和 Pending 等容器，遍历元数据，读取名称、类别、属性和依赖顺序，把实体放到相应位置。随后其他路径按条件推进初始化。

这很像先编排任务清单，再执行任务。把一条记录放入清单，既不等于已经调用 init，也不等于创建了 Linux 线程。

同样，某个函数尾部调用了清理函数，就不能因为它处在初始化末尾而称它为“进入主调度循环”。已有复核发现旧文档所说的那个尾调用实际涉及 chunk 清理，初始化例程会返回。

4.3 十三个类别

编号 名称 阅读提示

2 Library 公共库相关类别
3 Driver 驱动相关类别
4 Protocol 协议相关类别
5 Management 管理相关类别
6 Registry 注册与回调设施相关类别
7 SystemInit 系统初始化类别

编号不等于执行顺序。已有代码会读取另外的顺序映射。13 个类别也不能直接与 14 个 level_* module 记录配成同一张表。

4.4 线程 调度对象与消息循环

已有资料中同时出现 pthread、IOS 内部进程/任务名称、调度队列和定时器等线索。这些对象可能处在不同抽象层。

分析时可以分别问：谁分配任务对象？谁把任务放入队列？谁执行回调？谁调用线程 API？哪个循环实际取消息？把每一环对应到消费代码，比根据 Pending 或 process 等单词直接下结论更可靠。

当前现场已核对七条 Linux 线程：IOS 主线程、Fastpath、Packet、Auxiliary、Sim Aux 和两个 Worker。系统初始化 D7B7690 → 1583D9A0 调用外部 __be_mcp_spawn_threads；本次绑定在 libiosd_crb_vxe_unix.so。它登记现有主线程并创建其他执行环境，Worker 的线程池创建继续进入 libthpool.so。这条创建路径早于此处的 module 发现和 subsystem 分类推进。

Fastpath 和 Packet 的已审查入口使用 epoll 和回调分派；Auxiliary 消费辅助请求队列；Sim Aux 有另一套配置模拟相关请求；Worker 消费通用工作队列。业务归属需要继续关联提交者和具体回调，不能按七个线程名划分七个 subsystem。

level_* module 分组与 *_thread_level 的数字属于不同对象。后者经 D714C40 → D714A10 分配 Interrupt Stack 并登记执行上下文，例如 Packet level 2、Fastpath level 3；不是把线程优先级或 subsystem 类别填进同一张表。七个 TID、库内入口、线程表索引及更多解释见 iosd 的线程 任务与 level。

4.5 EHSA 怎样把心跳 状态机与平台连接起来

当前样本已经追到一个具体例子：ehsa_background_monitor 的 init D511200 创建 peer monitor 任务；ehsa_fsm 的 init D519D30 创建 FSM 任务和队列；platform_ehsa 的 init D52C3A0 安装平台策略与故障回调。它们是多个有明确初始化入口的实体，通过消息、队列和 registry 协作。

心跳发送经 D51CE00 封装类型 30 KEEPALIVE；接收分派 D51E0E0 经按类型注册的回调进入 D512810，刷新监测。peer monitor D510B80 的定时器或计数器分支可产生 KEEPALIVE_FAILURE，随后经过事件过滤和平台策略，再排入 FSM。超时检测、事件提交与切换完成是不同步骤。

FSM 由当前状态和 major/minor 事件索引动作表。本轮取得 14 个状态、224 个完整事件槽、19 个不同动作回调；状态 7 的名称以及部分事件来源仍未知，全部保留。D51AF30 动作可进入 D5156E0 的 Standby→Active 编排，准备不足时还有 reload 分支。队列消费者另有直接状态写入，不能把表内边当成全部状态变化。

核心函数体在 iosd 主 ELF 中。少量 GOT 读取与已加载模块范围对照表明，Chasfs 导入绑定到 libchasfs.so，能力查询 cyan_get_boolean 绑定到 libcyan.so，两项 MCP 平台接口绑定到 libiosd_crb_vxe_unix.so。平台能力允许时，故障路径中的回调会发布 notification/stby-request-swo 属性；消费该请求的外部进程和最终动作仍未闭合。

这个例子体现了初始化实体、内部任务、状态表、业务函数和进程边界之间的差别。完整说明、函数 RVA、条件与未知关系见 iosd 的 EHSA 心跳与主备状态机，全部表项可在 EHSA 证据目录 检索。module 的阶段依赖仍按独立机制记录，不把类别 8 自动当成 level_ehsa 的成员表。

5 CLI 语法图与执行入口

5.1 从一条简单命令开始

考虑已经恢复过的配置语法：

hostname <string> <cr>

hostname 是要匹配的关键词；<string> 表示参数；<cr> 表示到达输入结束位置。解析器沿着相应动作，检查输入并把参数写入上下文，最后才进入终结处理。

因此，一个关键词节点一般不是一条完整命令。把全文件的关键词去重后连在一起，也不能恢复命令。

5.2 accept 与 alternate

下面是结构示意：

入口
 ├─ 匹配 alpha → EOL
 └─ 尝试 beta  → EOL

若当前节点是 alpha，其 accept 代表匹配成功后的继续位置；alternate 可以代表不匹配时改试其他选择。沿 alternate 不应把失败的 alpha 附加到命令里。

正确结果可以是 alpha <cr> 和 beta <cr>。错误的遍历会把它们拼成 alpha beta <cr>。边的“是否消耗输入”必须由动作语义决定，不能只看有几条指针。

5.3 EOL handler 与 selector

EOL 是语法终结点。某些已解释的 EOL 描述符包含 handler 地址，并附带 selector。selector 可以理解成“同一个处理函数中的功能编号”。

路径 A → EOL，handler H，selector 1
路径 B → EOL，handler H，selector 2

这里有两个命令定义，却只有一个 handler。反过来，同一个 EOL 也可能被多个路径共享。因此 handler 数、EOL 数、路径数和命令字符串数不相等。

VPDN 的 enable 分支对应 selector 28。这个 28 是业务分派参数，不是 parser 动作表中的 opcode。

5.4 opcode 与动作表

动作编号描述“当前解析步骤如何工作”，例如匹配关键词、读取数字、检查条件或处理输入结束。当前样本的动作表有 314 个有名称槽位。

某些回调在静态数据中有值，另一些需要继续追踪运行时注册。空回调只说明当前静态表示缺少它的执行入口，不说明对应语法定义不存在。

当前提取器能解释部分 keyword、number、string、address、predicate、comparison、state assignment 和 EOL 等动作。未知动作继续作为不透明步骤保存。

5.5 共享后缀与循环

路径 A ─┐
        ├→ 公共后缀 → EOL
路径 B ─┘

如果为了避免重复访问而在全局标记“公共后缀已访问”，就可能只输出路径 A，漏掉路径 B。枚举路径时，检测当前路径中的环，与对整个图去重，是不同操作。

当图中有循环时，不能声称用一份有限字符串清单列出了全部可能输入。更合适的保留方式是保存图、循环边、参数规则和枚举停止位置。

6 解析上下文 条件与配置生成

6.1 CSB 是处理一次解析所需的上下文

解析器需要记住：正在处理哪一种输入、用户给了哪些参数、当前模式是什么、最终交给 handler 的 selector 是多少。项目把这类上下文称为 CSB；不需要先猜出该缩写的完整厂商定义，才能分析它的读写。

当前路径模型只明确跟踪本样本的 sense、default、NVGEN 三个字段，其他状态仍可能影响行为。字段偏移只是本样本已经复核的局部知识，不是通用 C 结构定义。

6.2 正向 no 与 default

配置输入里，正向、no 和 default 可能走不同路径。例如：

hostname <string> <cr>
no hostname <cr>
default hostname <cr>

后两条可能省略正向所需的参数，因为上下文告诉 handler 这是撤销或恢复默认的请求。不能简单给正向字符串前面加一个 no，也不能认定所有命令都支持 default。

本样本路径模型的普通正向初始假设是 [sense=1, default=0, NVGEN=0]。这是用于生成一类示例的显式假设；候选定义池不使用它删除其他分支。

6.3 条件可以出现在多个阶段

阶段 可能遇到的条件
注册前 平台、初始化阶段、资源检查、回调结果
匹配语法时 模式、权限、参数范围、谓词、状态比较
handler 内 功能启用状态、已有对象、配置组合是否合法
消息或工作进程中 目标任务、队列、会话、内存与进一步业务条件

所以，“关键词能被匹配”只说明走过了一部分检查。即使到达 EOL，后面的 handler 或异步处理仍可能拒绝或失败。

6.4 NVGEN 的方向与输入解析不同

普通 CLI 解析通常从输入文字走向参数和处理函数；NVGEN 关注从当前配置状态生成配置文字。

输入解析：用户文字 → 解析上下文 → handler → 状态
配置生成：当前状态 → 生成回调 → 配置文字

某个函数同时参与两条方向，不能把它的 NVGEN 分支当作用户输入时一定执行的逻辑。配置生成得到的行，也不会自动列出所有隐藏、测试或尚未启用的命令。

当前样本的 show running-config 路径经 0xDFE9DB0 → 0xDFE8DD0 进入生成请求设施，核心 0xE0DE210 创建 NV Parser CSB，设置 NVGEN=1、模式和输出目标。普通生成分支通过 mode 对象 +0x50 取得语法起点，排入节点并调用遍历器；指定筛选回调时有另一条分支。生成前后的 registry 钩子还提供其他参与入口。

因此，“收集各组件配置”在这条路径中体现为沿配置语法和对象迭代进入回调，不是重新调用每个 subsystem 的 init。业务回调负责解释自己的状态，公共输出函数负责缩进、格式化和写入输出目标。全局槽 0x381E2E30 保存生成中的 CSB 上下文，不是所有组件状态的统一存储。

nvgens_action 的消费者 0xE39D8F0 从载荷读取回调与 selector，经过 0xE39D9B0 的状态门控后调用业务函数。例如 hostname 的 NVGEN 节点和 EOL 节点共用 0xE0E6A00、selector 0；接口 description 共用 0xE40C850、selector 3。函数在普通路径更新状态，在生成分支读取状态并输出。

当前还确认接口配置文本缓存：命令 parser config cache interface 的 handler 为 0xDEF9650，开关变量为 RVA 0x381C05B0。接口生成路径在已有缓存且资格检查通过时复用文本；否则生成片段，并通过回调保存到接口对象 +544。禁用路径创建专用生成上下文，遍历接口并释放缓存。当前开关值、各接口缓存内容和普通配置更新的全部失效触发点尚未验证。

保存图中的 5,099 个已解码 nvgens 节点，有 4,174 个与已解码 CLI EOL 同时共用函数和 selector。这个数表示描述符关联，不能换算成组件或命令数量，也不证明所有分支在目标上可达。

完整调用链、状态实例、缓存流程与原始证据见 iosd 的 NVGEN 与接口配置缓存。接口生成缓存、输入匹配用的 parser cache、ICM/diff 配置文本结构分别记录，不因名称相近而合并。

6.5 条件未求值意味着什么

报告中的 evaluated=false 表示没有执行目标谓词或确认条件真值。某些 evaluated=true 则只针对局部符号常量，例如路径中明确把 sense 设为 0 后进行比较。

不能把局部符号比较成立，理解成设备状态已经确认。报告没有 <?> 也只说明未经过已标记的不透明步骤，权限和参数 flags 仍可能未解释。

7 命令片段注册与链接

7.1 从完整命令拆成片段

大型程序不必把所有命令一次写成一张固定大表。一个公共模块可以提供前缀，另一个模块提供后续片段，在初始化或某个业务动作中把它们接起来。

结构示意：

公共部分：show → [链接位置 A]
特性部分：statistics → <cr>

把特性片段安装到 A 后：show statistics <cr>

本项目把片段入口叫 root，把用来匹配安装位置的标识叫 link key。key 的具体表示由消费代码决定；当前样本中有地址形式的 key，它不是用户输入的关键词，也不是 selector。

7.2 注册表与链接槽是两件东西

注册表描述“哪个片段想接到哪个 key”；链接槽描述“这个 key 对应的实际连接位置”。

对象 示意表示 你能从中得到什么
注册记录 key A → fragment R 某片段要提交到 A
链接定义 key A → anchor S，type 1 A 的入口连接位置是 S
安装行为 修改相应链接，把 R 接到 S 运行时树或链发生变化

所以，找到注册记录不等于读到了安装后的内存结构。静态分析器可以增加一条“候选安装边”，表达这种可能连接，而不修改 IDB 或调用目标注册函数。

7.3 当前样本的三种记录

记录 大小 相对记录起点的重要字段 作用
静态注册项 16 字节 key +0，片段 root +8 提交哪个片段
核心静态链接槽 48 字节 key +0，anchor +16，type +24 已在静态表中定义的连接位置
动态链接记录 56 字节 next +0，key +8，anchor +24，type +32 运行时分配并挂入链表的槽

动态记录前面多了 next 字段，相同概念的字段因此相差 8 字节。看到代码以“动态记录加 8”作为内部视图时，要先确认这个起点变化，避免把两种偏移混用。

这里的大小与字段都是当前样本的局部布局。跨构建仍需验证；静态指针与运行时 tagged BE 指针也不能用同一种读取规则糊在一起。

7.4 入口链接与返回链接

当前消费代码区分 type 1 和 type 2。为便于理解，可以把它们分别看成入口方向的片段安装和返回方向的连接。

公共前缀 → [入口槽] → 特性片段 → [返回连接] → 公共后缀 → EOL

只找到片段的开头，可能还不能拼出完整命令。只有把返回连接、公共后缀和模式入口一起考虑，才知道关键词前后还有什么内容。

type 1 的已核对安装路径涉及 alternate 链；type 2 的建模还有特定链接占位值的前提。这是消费代码的行为，不是“任意两条指针都可随意连接”的通用图规则。

7.5 动态槽什么时候出现

创建槽通常涉及分配记录、写入 key/anchor/type、挂到表头。程序可以在系统初始化、功能首次使用或其他共享初始化路径中执行这件事。

动态槽的创建代码可以静态分析，动态槽的堆地址与当前内容要从运行时观察。两种知识并不矛盾：没有 dump，也可以知道“哪些代码可能创建它”；有 dump，才能知道“这次运行创建到了哪里”。

7.6 找不到槽时不一定失败

当前样本存在待绑定队列。某次注册找不到 key 对应的槽时，可以先保存请求，返回值仍可能表示请求已被接受。之后创建槽会改变重试状态，解析入口再尝试绑定这些记录。

提交片段
  ├─ 槽已存在 → 尝试安装
  └─ 槽不存在 → 进入待绑定队列
                         ↓
              后续创建槽，触发重试
                         ↓
                  再次尝试安装

因此，应分别记“提交成功”“排队成功”“安装成功”。用户观察到后续命令过一段流程才出现，不一定意味着第二条用户命令专门执行了注册；也可能是之前排队的请求终于有了安装位置。

8 间接调用与状态依赖

8.1 直接调用与间接调用

直接调用的目标写在指令或已解析表达式中。间接调用先取得一个函数指针，再调用这个指针。

/* 结构示意 */
slot = get_callback_slot();
fn = decode_pointer(*slot);
fn();

只收集 call 某地址 会漏掉后者。接下来要找：谁向这个槽写过函数地址？写入发生在什么条件下？调用时读取的是不是同一个槽？

8.2 getter 帮助识别槽

某些短函数返回“某个全局对象的固定偏移处”，相当于取得一个回调槽的位置。它们常被称为 getter。

如果一个函数向 get_slot() 返回的位置写入 init_feature，另一个函数从相同 getter 返回的位置取函数指针，就形成一条候选绑定关系。

写入者 W → 槽 S ← 消费者 C
           │
           └─ 候选目标：init_feature

据此建立 C → init_feature 的候选间接调用边

称为候选，是因为 getter 可能有环境分支、对象可能重建、后面还可能有覆盖写入。静态找到一处赋值，不能当成每次运行的实际槽值。

8.3 局部变量的多个来源

反编译中经常看到 v1、v2 这类局部变量。变量可能在不同分支被多次赋值。

/* 结构示意 */
if (condition)
    p = slot_a;
else
    p = slot_b;
call_through(p);

正确的候选分析应保留两个来源及条件。按文本只取“最后一次赋值”，可能漏掉 A；把两个来源都判成必然执行，则又过强。goto、循环和早返回还会使单纯按文本顺序的分析更不可靠。

8.4 状态依赖怎样建立

最基本的状态依赖是一处写入和另一处读取指向同一个变量：

命令 A 的某个分支 → 写变量 X
命令 B 的解析或执行路径 → 检查变量 X

这表明 A 可能改变 B 的条件。要说“执行 A 一定放行 B”，还需要证明写入值、检查关系、控制流和其他条件。

通用分析器因此先把 X 叫作未分类状态变量，而不自动命名为 enabled、hidden 或 initialized。名字要由消费代码和上下文逐步确认。

8.5 四种容易混淆的前置关系

A 做了什么 B 后来为什么可能可用 静态分析应找什么
创建动态槽 之前的片段有了安装位置 创建 API、key、anchor、待绑定队列
注册新片段 解析器增加了可达语法 注册表、入口与返回连接
改状态变量 已有语法的谓词或 handler 检查通过 写入者、读取者、比较关系
创建工作进程或对象 命令能分派，但执行终于具备依赖 PID、队列、对象查找和失败路径

真实案例还可能把这几种关系组合起来。不能因为现象都是“后来可用了”，就把所有原因统称为“隐藏命令注册”。

8.6 静态分析为什么有价值

一次运行快照只显示某个时刻、某个平台状态中的对象。静态文件还能保留尚未触发的创建代码、未安装的片段和当前条件为假的分支。

不过，静态分析也不是无所不能：计算生成的数据、外部库、复杂间接调用和未知动作可能仍然缺失。合理的目标是把潜在定义和条件保存下来，用动态观察补充，而不是让其中一方删除另一方的证据。

9 配置树 diff 与 CDL

9.1 语法树与配置文本树

语法定义描述可以输入什么；配置文本树保存某组配置行及其层次。

语法定义：description <string>
配置文本：description branch-office

前者是一条规则，后者是带具体值的一行文字。配置文本可能只覆盖已经配置、已经生成或参与比较的内容，不能反推出所有可输入规则。

9.2 ICM 的已核对观察

现有 ICM 相关消费路径处理 72 字节节点、配置文字、层级和差异。节点的 +0 用于向下遍历，+16 用于回溯，+24 用于同级遍历，+8 参与树链维护。没有在这套节点中确认 +8 为 handler。

文本通常涉及 +48 以及 flags、索引和缓冲区。某些路径把 +60 当作开始偏移，把 +64 当作结束偏移，读取长度为：

长度 = 结束偏移 - 开始偏移 - 1

还存在通过根对象的数组间接取得缓冲区的路径，不能永远把节点 +48 当作可直接读取的字符串地址。

这些字段与 40 字节静态 transition 不同。把两种结构的偏移表混起来，会读到看起来像地址、实际意义却完全不同的值。

9.3 diff 树用来表示什么

diff 可以理解为两份配置之间的差异处理。结构示意：

旧配置                         新配置
interface GigabitEthernet1     interface GigabitEthernet1
 description old               description new
 mtu 1500                      mtu 1500

两份文本里 MTU 相同，description 不同。差异结果还需要知道 description 属于哪个接口上下文。

已有代码观察支持比较节点层级和文字、设置匹配标记，再按 old/new 方向生成差异输出。具体怎样形成撤销命令和执行顺序，需要继续看消费路径；这个例子本身不证明自动生成什么设备命令。

旧笔记中的 diff 临时根不能当作全系统 CLI 主根。也没有充分依据断言整个程序只有一棵命令树。

9.4 CDL XML 是另一份命令描述来源

当前 cdl.xml 的文件头把它标为 BinOS Command Set。它有 keyword、value、EOL、filter、request 以及带注解的边。

它与 iosd 静态语法图在“都有关键词和分支”这一点上相似，但对象相似不等于集合相同。项目没有证明 iosd 自身直接加载这份 CDL，更没有证明它完整覆盖 IOS 配置模式。

已有资料把 CDL 与 Shell Manager 一侧的命令描述联系起来。Shell Manager 可以先理解成系统中的命令管理或路由边界；精确加载流程及其与 iosd 的接口仍需对相应二进制核实，不能由名字补出一条完整调用链。

9.5 为什么旧 CDL 遍历会漏路径

CDL 存在共享后缀。旧 C++ 遍历规则对全图使用了屏蔽已访问节点的方式，可能在第一条路径之后不再沿共享后缀输出其他路径。

新遍历器区分图中节点去重、当前路径中的环检测、路径计数和示例输出，并保留边上的 filter-ref、set、set-tdl 等注解。过滤器不直接出现在显式边端点，并不表示它没有影响。

内部 name 与用户输入关键词也不相同。当前文件中输入文本通常看 str；按 name="interface" 的次数判断有没有接口命令，是不可靠的。

9.6 应该怎样使用 CDL 结果

当前主根显式图有 4,372 个可达 EOL，结构路径计数为 652,569,212。默认只输出 4,772 条有边界的示例。路径数既没有展开参数的全部取值，也没有求出过滤条件的真值，所以不是六亿多条可执行命令。

config 子图取得的两条完整路径是 config hw-obfl dummy <cr> 与 config sdm dummy <cr>。这不是通常 (config)# 下所有命令的列表，也不证明这两个模板在设备上可用。

CDL 适合用来比对相同文本、发现差集和提供额外上下文。差集本身仍不能证明某命令 undocumented：版本、平台、模式和描述来源都可能不同。

10 消息 数据模型与转发接口

10.1 三种不同的 handler

CLI handler 处理解析后的上下文；消息 handler 处理某类消息；事件或 registry 回调处理某个事件或查询。它们都可以是函数指针目标，但入口语义不同。

一个名字带 _message_handler 的函数不应直接当作 CLI 命令终点。若 CLI handler 先发消息，真正的业务动作可能在另一个工作进程的消息分支中完成。

10.2 消息命名线索

已有材料中出现 _message_handler、_message_dispatch、_message_dispatch_init、_message_create、_message_destroy 等命名族。

这些名称可帮助找入口、分派和生命周期。确认注册关系仍需看谁把消息编号与哪个函数关联起来，分派时如何查找，以及数据怎样编码。

消息驱动是重要的交互方式，但不是说 iosd 没有普通直接函数调用。两条途径可以同时存在。

10.3 MQIPC 与进程边界

MQIPC 是项目中一组消息队列 IPC 接口名称。mqipc_enqueue、__be_iosd_write_one_mqipc_msg 等可以帮助定位跨进程通信线索。

跨进程消息与进程内消息可以都承担分派职责，但不能据名字相近就认定它们共享同一套结构、编号或序列化格式。

10.4 VTY 与 Web 管理入口

已有符号中可见 VTY 请求消息及处理函数，提示某些 CLI 输入会经过会话和消息封装。分析应从实际会话入口追到解析器，而不是假设每种 console、SSH 或 Telnet 路径都完全一致。

已有笔记还记录了 WSMA、wsman、nginx、Lua 脚本以及 WSMAGetData、WSMAApplyCmd 等线索。它们可以用来研究部分管理请求怎样转换为 CLI 或配置操作。这里不把“所有 Web 操作最终都走同一 CLI 路径”作为已确认事实。

10.5 数据模型与 tbl 接口

tbl_* 名称可以提供特性、表或字段访问线索，例如协议状态和许可状态相关名称。但完整名称中可能含多个层次，不能只按下划线机械切出表名与字段。

也不能仅由前缀认定它必然由某份 YANG 生成、必然属于 confd 的某个库，或者与 CLI 定义一一对应。要看参数、对象布局、调用者和返回值的实际使用。

10.6 控制面与转发面

路由计算、配置控制等可以与实际报文转发处在不同路径。FMAN-RP、FMAN-FP、QFP、CEF、RIB、FIB、punt 等术语有助于辨认这一边界。

当前材料提示通过转发管理相关接口交换状态和控制消息。物理或虚拟实现依平台而异，不能把整个转发面说成某一个普通进程，也不能假设所有数据面交互只经过同一条固定通道。

11 静态证据与覆盖范围

11.1 从线索走向消费代码

一个实用顺序是：先用段名、名称、字符串或 magic 找到候选，再看读取这些数据的代码，确认字段和动作语义，最后编写提取规则。

例如，有一个日志字符串写着 parser_add_command。它可能出现在上层包装器或错误处理分支。只有找到实际读取 key/root 记录并安装链接的消费者，才能建立相应解析器。

11.2 保留原始层与解释层

原始层保存输入身份、地址、字节、调用点和读取失败。解释层保存关键词、参数范围、条件、候选 handler、注册边和状态关系。

解释层可以逐步修订；原始层让你能够回查修订依据。未知动作不能因为暂时不能显示漂亮命令，就从原始图里删除。

11.3 定义池与路径示例

候选定义池保存已经取得的节点、边、注册片段和未知项。路径示例从图里选一条或多条可读路线，帮助人理解结构。

图和定义池：保留全部已取得的分支与循环
路径示例：为了显示，选择有限路线

当前普通路径恢复偏好较少不透明步骤、较少输入 token、较少边。这会显示较简单的例子，却可能省略可选词和别名。VPDN 的小片段后来另行枚举，才把这些形式显出来。

11.4 没有 dump 也能做什么

可以发现静态描述符，解释部分动作，关联 EOL 与 handler，查注册代码、动态槽创建代码、函数指针写入和状态读写。对许多命令来说，这已经能得到很有价值的语法与依赖候选。

不能仅凭这些信息保证设备上一定可用，也不能承诺已经覆盖全二进制。静态未知链接、计算生成的数据和外部代码仍可能需要运行时材料。

所以，“完整分析是否必须有内存”应该分对象回答：恢复某些静态定义不必须；确认某次运行的堆对象、真实槽值和当前状态，则通常需要相应运行时证据。

11.5 四种不同的覆盖问题

问题 应看的内容
起点是否取全 已发现 root、未选 root、未解析调用、其他注册方式
图是否走完 pending 节点、数量限制、环、读取失败
语义是否解释全 未知 opcode、载荷错误、不透明动作、参数 flags
条件是否在运行中成立 模式、权限、实际注册、状态、对象和资源

completed 表示某扫描步骤执行结束；complete_for_configured_edges 表示配置起点和已知边的遍历结束。它们都没有同时回答上面四个问题。

11.6 去重时保留什么身份

同一关键词可以出现在不同模式和片段中；同一个 handler 有多个 selector；同一个 EOL 有多个路径。合理记录至少包括来源、模式候选、root、EOL、handler、selector 和条件。

候选间接调用也应保留是哪一处槽写入、哪一处消费，以及两侧各自的条件。不能只把两个函数地址连起来，就忘掉为什么曾认为它们有关。

12 VPDN 注册与状态案例

12.1 先提出一个可以验证的问题

问题不是笼统地问“VPDN 有多少命令”，而是：哪条输入会到达某个注册分支？这个分支提交什么表？表接到哪里？同一输入是否还修改了别的状态？

现有静态案例已经把直接触发分支定位到 (config)# vpdn enable，对应 selector 28。以下结论限定于当前样本已审查的普通非 simulation 分支。

12.2 第一步 进入 enable 分支

简化后的逻辑如下。它是逻辑摘要，省略了其他业务初始化，不是目标源码或设备脚本：

若正在 NVGEN：走配置生成分支，返回

若 selector 为 28：
    若为正向 sense：
        执行资源回调检查
        若有活动回调否决：报告错误，本分支不写启用状态
        否则：
            若首次跟踪初始化尚未尝试：尝试相关初始化和共享回调
            写 VPDN 启用状态
            调用运行初始化辅助函数
            若测试初始化尚未尝试：
                调用测试初始化例程
                设置测试初始化尝试标志
    否则：
        清 VPDN 启用状态
    返回

其他 selector：
    若未启用 VPDN：在业务分派前返回错误
    否则继续处理各 selector

资源检查是一个回调列表。未停用成员中，任意回调返回非零，都可能否决本次正向请求。已找到的一名具体成员在正常返回时给出 0，但这不能代替运行时完整成员列表。

12.3 第二步 区分几个独立状态

书中简称 意义 不能由它直接推出什么
E VPDN 业务启用状态 所有相关片段已经安装成功
T 首次跟踪初始化尝试标志 共享回调本次一定完成全部工作
R 测试初始化尝试标志 注册、内存分配和工作进程都成功
S 共享 SSS 首次初始化标志 它只可能由 VPDN 触发
P VPDN test 工作进程标识 进程仍存活且消息一定能完成
B scalability 批处理状态 所有其他测试命令都被同样限制

这些称呼来自各变量的具体消费代码。通用分析器不能看见一个 byte 就自行给它起这样的业务名称。

12.4 第三步 跟到直接注册片段

测试初始化例程提交一张 key/root 表。对应 key 在核心静态槽表中已有定义，片段接到 EXEC 的 test 前缀下。这一支是“已有槽上的按需安装”，不能称为新分配了动态槽。

片段有 58 个已取得地址，14 个 EOL，对应 19 条已建模无环语法模板：

相同 selector 的不同形式说明最短路径会遗漏可选参数。参数取值、权限和业务结果仍需分别核对。例如 selector 9 的语法范围是 0..65535，但 handler 又限制可支持的 RADIUS code；不是范围内每个数字都有效。

片段还有 25 条边界路线，其中 24 条指向 IDB 未初始化地址，1 条是 parser stop。报告保留了这些路线，没有把它们算成完整命令，也没有因不完整而删除。

12.5 第四步 注册之后还要怎样执行

部分 selector 把消息 3855 投递给 VPDN test 工作进程，工作进程再按 selector 分派。因此它们依赖 P 和消息发送结果，有些还要分配请求对象。

这里的 P 指代码中用于消息投递的工作进程标识；尚不能直接把它当作 Linux ps 显示的 PID。第1章所说的执行实体层次，在这里同样适用。

selector 9、10 直接设置测试状态；selector 13 直接调用查找和重置相关函数，不经过相同的 test 消息队列。selector 11 还有“已处于批处理状态则等待”的检查。

所以，不能用一条“VPDN 已启用”边代表所有测试命令的执行条件。

12.6 第五步 跟到间接 SSS 分支

首次跟踪初始化还会调用某个 getter 返回槽中的函数。静态找到的一处赋值候选把该槽指向共享 SSS 初始化函数；它在首次分支里进一步提交另一张注册表。

这张表有 6 个 subscriber 跟踪片段，涉及相关动态链接定义及公共父级。例如恢复出的候选示例包括：

EXEC:
  show monitor event-trace subscriber vpdn event <cr>
  monitor event-trace subscriber vpdn error enable <cr>

configure:
  monitor event-trace subscriber vpdn event size <number:1..1000000> <cr>

这条链涉及 9 个已审查的相关动态槽定义，但共享初始化并不专属于 VPDN。其他功能可以先触发它；实际槽绑定、创建成功与顺序仍要用运行时证据核验。

12.7 第六步 检查关闭与再次启用

已审查的 no/default vpdn enable 分支只清 E，没有复位 R/T，也没有在该分支调用注销测试片段的函数。

这带来几个重要区别：

  • 同一配置 handler 的其他 selector 会因为 E=0 被拒绝；定义却可能一直存在。
  • 测试片段可能仍保留在解析结构中；测试 handler 没有同样的直接 E 检查，但进一步操作仍可能失败。
  • 再次启用时若 R 已为 1，测试初始化例程会被跳过；前一次初始化的某些失败未必自动重试。

资源回调否决的分支，也没有把既有 E 强制清零。因此不能把“一次 enable 失败”直接记成“状态一定为未启用”。

12.8 从案例抽出通用研究模板

研究任何类似线索，都可以依次记录：触发 handler 和 selector、入口条件、状态写入、直接注册、间接槽写入与消费、片段的入口和返回、业务分派、失败与撤销路径。

这是一组应调查的问题，不是要求所有命令都遵守 VPDN 的固定状态机。

案例原始证据与完整条件见 VPDN 激活链报告。

13 通用分析结果与证据关系

13.1 通用指什么

通用分析核心根据 API 角色、参数表达式、调用关系、函数指针绑定和状态访问工作。业务 handler、命令名称和状态变量地址不写死在算法中。

但 API 的地址、参数位置和结构布局仍需要样本 profile。当前 profile 绑定已知输入 MD5，保存的是 API RVA。算法不依赖 VPDN，不等于已经适配所有架构、版本和构建。

13.2 两种证据来源

来源 得到什么 使用时的边界
结构化 ctree 采集 从反编译表达式取得调用、赋值和部分条件，尽量保留指令位置 仍是有界采集，不是完整 CFG 可行性证明；本轮完整实机采集尚未验证
缓存反编译文本导入 IDA 不可用时，离线取得有限表达式和调用候选 只识别文本子集，字符位置不是指令地址；未知原文继续保存

ctree 可以理解成反编译器提供的表达式与语句结构；IR 是分析器保存的中间表示。例如它把一条赋值保存成左侧、右侧、所在函数和条件等字段，方便离线关联。

两种来源都没有执行目标 handler 或谓词。文本中明确看不到的字段不能自动补出；没有独立样本身份的缓存也要标记，不能与已核对输入的材料说成同一种强度。

13.3 先看摘要再看候选组

先看 identity 确认输入，再看 scope、采集来源、数量限制和未知项。然后选一个 handler，查看其命令定义组和通向注册事件的调用链。

通用报告里的候选组往往有多个 selector。它表达“这个 handler 中存在到注册事件的关系线索”，不表达“该组所有命令都会执行这条注册”。VPDN 的手工深入分析之所以有价值，就是把候选组进一步缩到了 selector 28。

13.4 看动态槽表时问三个问题

第一，key 和 anchor 是从具体参数恢复，还是仍是未知表达式？第二，创建代码在什么条件下执行，返回值有没有检查？第三，实际堆地址是否已经观察到？

“创建调用证据”不是“已经分配的槽数”。同一调用还可能同时有直接引用和文本来源，统计记录可能重复表达一个实际事件。

13.5 看间接调用和状态表时问什么

间接调用要看写入与消费是否指向同一个候选槽、是否可能被覆盖、编码是否一致。状态依赖则看写入和读取的对象是否相同、读取是不是判断条件、关联到哪些 selector。

write_may_affect_guard 的含义是“写入可能影响某个条件判断”，其中 may 不能省掉。若只是影响普通读取，报告使用另一种关系，不应一概称为解锁。

13.6 当前结果应该怎样解释

保存的通用结果包含 10,479 条新取得的直接 API 引用，结合 132 个缓存函数形成 61 组触发候选，涉及 31 个 handler。缓存中 59 个附带匹配身份，73 个缺少独立身份字段并保留标记。

候选中可见 segment-routing mpls、metadata flow，以及 bulkstat 等经过公共模式创建链的线索。共享链可能是模式设施的公共工作，不一定给每条业务命令安装一组专属新命令。

结构化采集在接口兼容修正后的请求发生超时，之后停止派发新请求。本文使用的是已保存材料和离线结果，没有把未返回的采集当作成功。

14 rebase 调试器与 core

14.1 rebase 期间的数据边界

IDA 正在 rebase 或 attach 时，可以处理已有 HTML 和 JSON；扫描、批量反编译与动态采集应等数据库恢复响应、地址基准稳定后进行。

这既避免给 IDA 增加工作，也避免把重定位前后的地址混入同一次采集。先前某个请求超时，只能说明客户端没取得完整结果，不能证明服务端立即停止，更不能证明某个函数不存在。

14.2 rebase 与地址映射不是同一个动作

rebase 改变 IDA 数据库中映像的坐标。地址映射则告诉插件，当前 IDB 与运行时内存怎样对应。

一个数据库可以已经 rebase，但仍然需要确认它是否与当前进程使用同一个映像基准。映像再次装载或换一份 core 后，也要重新核验映射。

旧报告 EA ──减旧基址──→ RVA
                          ├─ 加当前 IDB 基址 → 当前 EA
                          └─ 加运行时映像基址 → 运行时 VA

不要把旧 JSON 中所有整数统一加偏移。原始字节、字段偏移、selector、opcode、参数范围和 flags 都应保持各自含义。

14.3 旧 profile 与新 RVA profile

旧静态语法 profile 使用与 MD5、imagebase=0 绑定的地址。它在 rebased IDB 中拒绝运行，是为了防止访问旧位置。只改 idb_imagebase 或删校验，并没有自动修正其他地址和字节表示。

新生命周期 API profile 用 RVA 定位 API，因此可以在当前基址上计算对应 EA；旧语法报告仍保留自己的采集身份，用 RVA 关联。rebase 前的采集检查点不直接 --resume 到新基址，应该使用新的采集文件。

14.4 第一次真实内存读取的顺序

以下步骤只在 rebase 完成、界面恢复后进行。

  1. 确认目标暂停，记录当前输入 MD5、IDA imagebase 和运行时映像基址。
  2. 重新运行 dev_load.py，关闭旧会话窗口并建立新的插件实例。已导出的旧报告继续保留。
  3. 选择 debugger 数据源，重新设置并核验映射。
  4. 用已知、稳定且没有重定位或动态修改影响的字节检查一个小锚点。
  5. 先读取一个模块内全局槽，确认原始字节和指针编码。
  6. 再读槽指向的一个运行时节点，核对字段和 next。
  7. 最后才做带上限的链表遍历，导出来源、基址、原始字节、错误和边界。

一个锚点一致，只证明这个局部位置对得上，不是整个 core 或进程身份的充分证明。不要选会改变的业务状态当作恒定字节锚点。

14.5 动态槽链表要怎样读

新运行时入口按 profile 读取动态链接和待绑定链表。基本顺序是：

head 的 RVA
  → 换成运行时 head VA
  → 读 head 槽的 8 字节
  → 解码得到第一个堆节点 VA
  → 读记录、保存字段、取得 next
  → 重复，直到 NULL、循环、错误或数量上限

head 地址与第一个节点地址不能互换。重复 key 也不自动去重，因为它们可能代表多次创建、不同记录或不同阶段。

字段指针落入已确认模块映射时，可以附带 RVA；堆节点本身仍保存运行时 VA。未知内存读取失败会形成边界记录，不自动改读 IDB。

14.6 core 的特点

core 是某次采集的内存材料，不是一份新的源代码或语法全集。当前插件只支持相应的未压缩 ELF64 x86-64 ET_CORE 和 PT_LOAD 读取；压缩文件先在外部解压，厂商私有格式不默认兼容。

若 PT_LOAD 的内存范围大于实际收录的文件字节，剩余页面是“未捕获”，不能按普通可执行文件 BSS 的习惯补零。旧笔记中记录过设备侧 dump 手段，但它们的可用性、权限和具体语法依环境而异；本文的操作从匹配的既有 core 开始。

IDA 可以继续打开对应 iosd 的 IDB，由插件另外读取 core。这样，静态代码与运行时页面是两个来源，关系由映射明确建立。

14.7 为什么当前读取不叫原子快照

插件每次读取检查映射，debugger 后端检查目标暂停；但当前没有跟踪一次 resume 后再次 stop 的事件世代，也不能把多次网络读取说成一个瞬间完成。

因此读取期间保持目标暂停，分别保存每次采集。报告中的 atomic_snapshot=false 是对一致性范围的说明，不是让你把缺失状态补成“应该如此”。

14.8 首次暂停现场：从候选图走到实际连接图

本轮 attach、rebase 和暂停后，已对真正的 iosd 主模块核验三个不可变字符串锚点。一个实际遇到的错误是：IDB 打开 iosd，但调试器 attach 到启动管理程序 pman。此时 IDB 字节正常，调试地址读取失败。重新 attach 到 iosd 并核对模块与锚点后，才继续读取动态链表。不能用数据库 MD5 代替调试进程身份核验。

运行时命令图与静态对照 保存了本次结果：动态链接槽 1,783 条，待绑定记录 245 条，两张链都读到 NULL。报告同时导出模式路径示例树、已取得的实际连接图、全部静态注册对照和未知节点。槽记录数与示例路径数都不是命令总数；某个片段已挂接，也不等于权限、条件和 handler 一定允许执行。

service internal 是第二个状态依赖案例。当前样本恢复到配置模式 handler RVA 0xDE9A730、selector 20。启用变量 RVA 0x37B1B5F8 当前为 0；部分关键词的访问检查直接读取它，值为 0 时拒绝。首次启用还遍历两张已有命令描述链，按字符串定位权限描述并修改标志。两张链的 77 条原始条目全部保留；它们不是“新注册了 77 条命令”的证据。

因此，运行一条命令后出现更多命令，可能来自链接注册，也可能来自状态门控或权限描述变化。必须看实际写入、注册 API 和连接关系再分类。当前已审查的 service internal 辅助链支持后两种解释，共享回调的后续效果仍保留未知。方法和离线复现见 运行时命令图导出说明。

后续 config 模式补读与恢复 已读回原来的 26 个缺页范围，并沿新引用继续补读。当前已知图的缺页队列为 0，但仍有未解释的动作和条件。“取得字节”和“理解语义”是两个不同进度。本轮也修正了已审查公共回调的 RVA/VA 比较，重新区分正向、no、default 上下文；旧路径数与新路径数不能直接解释为设备增加了多少命令。

再往后，关键词选项表和间接分支提供了另一类线索。一个节点可能包含整个选项集合；有些集合由生成器临时构造，而非以持久链表保存。应分别保存每个词、取值、状态效果和条件。优先路径示例只选一个词时，其他词仍须保留在条件图中。两类消费代码及阅读方法见 config 关键词选项与条件回调 和 本轮报告。

15.8 如何理解测试通过

你可以在不连接 IDA 的情况下运行：

python -m unittest discover -s tests -q

它证明这些测试条件下的实现行为，不证明 Cisco 目标上的所有结构已经确认。实际 debugger 链表与语法采集已有样本验证，真实 core 的完整采集流程和结构化 ctree 全流程仍需分别验证。

合成 fixture 用于分层验证：生成微型 ELF/core，先检查地址映射，再读一个节点，再触及未捕获页面。它让你区分“读取器有问题”和“真实 iosd 布局还没理解”的两类错误。

完全离线的验证命令：

python tools/make_fixtures.py
python tools/inspect_core.py tests/fixtures/generated/fixture-iosd.core 0x555555564000 --layout profiles/icm_conservative.json

这里的地址属于合成 fixture，不是真实 iosd。它的验证基准是 IDB 映像基址 0x400000、运行时基址 0x555555554000、节点运行时地址 0x555555564000。你应能看见示例配置文字，handler 保持未解析；若读取到未收录页面，应报告缺失而非补零。

合成 fixture 可用于比较 IDA 的段、内存视图与 Python 输出，无需切换或修改真实 iosd 分析现场。

15.9 初始化组织地图

初始化组织地图 将 subsystem 和 module 分开浏览，保留完整候选记录与原始证据。在 IDA 重新加载开发版后，选择 Architecture: browse saved subsystem/module organization map，打开 reports/iosd-architecture-20261029/architecture.json。

类别列表进入对应 subsystem 候选，module 列表区分 group_node 与 callback_node；链接中的 prerequisite 表示 A 的前置依赖含 B，member_of 表示 A 归入 B 分组。双击记录可查看证据并跳转当前 IDB 中的地址。这里没有把某个 init 的全部可达函数判为它的私有代码，也没有恢复所有协议的收包和解析路径。

16 潜在未公开命令的研究方法

16.1 不要用是否漂亮决定是否保留

一条候选路径含未知动作、没有已知模式、暂时找不到 EOL、尚未安装或当前条件为假，都可能仍有分析价值。用户关心的命令恰好可能藏在这些区域。

保留不等于认定有效。可同时保存“定义存在的证据”和“尚未解释的部分”，把未知变成可继续调查的位置。

16.2 一个可重复的研究流程

  1. 记录输入身份、采集基址、数据源与工具版本。
  2. 从定义池挑一个候选，明确它来自哪个注册表或未知调用。
  3. 解释关键词、参数、入口、返回链接和 EOL，保存所有相关分支。
  4. 关联模式、handler 与 selector，区分匹配与业务处理。
  5. 追注册调用者、间接槽、状态写入与读取者，建立有条件的关系。
  6. 设计需要观察的槽、变量或对象，等合适的运行时材料验证。
  7. 对同版本、同平台、同模式范围的资料做对比，再讨论文档覆盖。

这个流程中的每一步都能形成独立结果，不必等拿到完整内存才保存前面的工作。

16.3 对照实验应记录什么

如果后续需要观察某个功能前后的变化，先明确观察对象：是动态链接记录增加、某条 next 改变、某个状态值改变，还是工作进程出现。

对照前后保存独立快照和同一映像身份。设备操作由研究者在合适环境中控制；本插件读取证据，不自行执行目标命令或改写目标内存。

一次快照没有对象，可能是时机、条件或页面未收录；也可能确实未创建。把这些解释都保留为待区分的假设，比直接写“没有这条命令”更有帮助。

16.4 undocumented 是一个后续判断

“内部 test”“帮助不显示”“CDL 没有”“官方某一页没写”“静态定义存在”分别是不同观察。讨论 undocumented 时，应说清参照的文档范围和具体版本，并确认模式、权限和路径没有解释错。

本项目目前没有自动判定 hidden/undocumented。它首先做的是尽可能保留和组织潜在定义，使后续比较有依据。

ICM 的 +64 在已核对的缓冲区分支是结束偏移，不是无条件的字符串长度；+8 不作为已确认 handler 使用。EOL handler 来自另一套静态语法描述符，不从 ICM 的树链猜出。

标记值也应分开：子系统扫描使用双 0x15055CC1 的字节线索；module header 的已观察标记对是 0x15055CC1 / 0xAFECAFEC；module link 的原始小端标签包括 0xDFEADFEA 和 0xABEFABEF。消费者做字节序变换后，代码中的常量显示可能不同。标记、长度和偏移都不是要随 rebase 平移的地址。

本样本的解析上下文已用字段包括 sense 9328、default 9332、selector 9364、NVGEN 9636。它们是结构内偏移，rebase 时不加基址。

阅读大端字段时，0.6.2 可通过右键 iosd Helper → Integer display / BE interpretation... 选择数值显示：数据/汇编视图使用原生格式，Hex-Rays 为选中的常量追加解码注解。例如 dd 12000000h 可以显示为 dd BE32(18)。这项操作不改原始字节，也不证明所选字段一定应按大端或 tagged 指针解释；格式、恢复与临时注解的说明见 整数显示与字节序。

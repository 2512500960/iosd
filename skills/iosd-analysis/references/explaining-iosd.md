# 把 iosd 讲清楚

用户想理解程序时，先解释职责和连接方式，再提供函数入口；只返回 JSON、命中数或 RVA 列表不能完成这个需求。

正文以已经观察到的对象、职责、字段和处理方向组织。使用“输入分支修改状态，生成分支读取状态并输出文本”这样的具体表述；覆盖范围和待确认关系集中放在证据部分。面向读者的教程保持操作与程序讲解，省去交付要求、练习和任务安排。

## 先给一张能读懂的地图

按用户的问题从四个视角选起点：文件/进程边界、初始化组织、连接与执行设施、业务输入与状态。它们相互关联，不能把 module、subsystem、源码 component、协议、task 和 pthread 强制拼成单一包含树。

可直接复用 [从大 ELF 到运行机制](library/docs/iosd从大ELF到运行机制.md) 的八张图和按需正文；本地阅读页为 [架构图解](library/docs/iosd架构图解.html)。这些资料随 skill 分发，不需要原始 Cisco 文件就能阅读。图有源 SVG，适合按当前证据修改；重新生成使用 `scripts/tools/build_architecture_atlas.py --help`，显式提供文档、布局摘要及工作目录输出，不写安装目录。

图解绑定当前分析样本；它概括了不同日期取得的局部证据，不是一次完整运行轨迹。新文件可先用 `scripts/tools/inspect_elf_layout.py <elf> --expected-md5 <digest> --output <work>/layout.json` 离线取得容器结构。该工具支持 ELF64 的两种字节序，仅读元数据并校验文件身份，不自动应用 iosd 业务布局。当前八图生成器明确绑定已审查样本，不能给其他样本套图。

先说清“为什么大”：文件字节、虚拟地址范围、NOBITS、共享库、运行时堆与 RSS 分开解释。节、重定位、展开信息和诊断元数据不直接等于业务模块；执行变体的一个例子不能推广为全节或所有函数的用途。

## 具体功能应该形成一条解释

围绕当前问题串起：职责 → 初始化者 → 登记与消费端 → 输入/缓冲区 → 执行上下文 → 条件和解析 → 状态/输出 → 文件或进程边界。取得哪一段就解释哪一段；没接上的边用带原因的未知框，不虚构连续全链，也不因路径不完整删除候选。

研究人员应能从输出中回答：

- 这个功能接收什么，做了什么；配置路径、报文路径和事件路径如何区别。
- 某个具体关系是调用、登记、队列交接、初始化依赖、状态读写还是文件包含。
- 哪些状态由谁保存；CLI handler、NVGEN、协议消费者如何关联，尚有哪些门控。
- 关键代码位置和复核证据是什么；外部绑定或 IPC 消费方是否真正找到。

同类功能可归纳经验，但保留反例。例如 CDP 展示先入队再由 task 解析；不能要求所有协议都照此实现。BGP 的消息分发与 TCP 字节流组装要分别定位。Auxiliary 展示循环在 so、接口与回调可在主 ELF；这不证明每个线程都跨越相同文件。

## 让图和证据互相指向

小的静态关系可直接用 Mermaid；需要导出和长期阅读时使用随附 SVG/离线阅读页或项目现有图工具。概念图标明“示意”，样本图写身份、RVA 与适用条件。图上不必堆全部地址，可把具体证据放在对应段落和可折叠说明中。

不同边分别标注含义；实线也不能默认为直接调用。回调传递、登记、当前绑定、当前执行是不同证据。所有权应限定到有证据的文件、函数或记录，不把 init 的全部可达公共函数独占归给某个 subsystem。

有价值的 insight 需要同时解释它影响什么、由哪些局部事实支持、适用条件和未知边界。设计意图若只是从实现归纳，用“推断”明确标记。任务最后给出能实际继续的入口，例如待核对的槽消费端、队列生产者或状态写入者。

本文记录 2026-10-30 在 IDA 9.1、新加载并完成 rebase 的数据库上的复核。样本 MD5 为 `9eccfd46caadfff9c18557e2a446e19b`。以下地址均为 **RVA**；当时 imagebase 是 `0x555555554000`。堆对象地址不能按 RVA 解释。

## 先理解两张图

理解一个协议，需要同时建立初始化图和输入处理图。

初始化图回答“谁准备了这个功能”：subsystem init 安装回调、申请队列、建立内部 task、初始化状态。输入处理图回答“这份报文怎么走”：分发者选择回调，回调可能把报文入队，另一个执行上下文才真正检查字段和更新状态。两张图通过登记与消费关系接起来。

因此，沿 init 展开直接调用图会漏掉以参数传入的回调；把 init 里所有回调都叫收包函数，又会混入接口变化、清理、认证查询和计时处理。这个区分适用于下面几种不同机制，具体地址仅适用于本样本。

## CDP：入队、内部 task、TLV 与邻居缓存

本轮复核得到的局部处理链是：

```text
CDP init CD878F0
  → CD894C0：有条件地创建 “CDP Protocol” 内部 task，入口 CD89F00
  → CD89F00：创建 “CDP packets” 队列，并登记 (65, CD8AB90)

CD8AB90：接口/启用状态与队列容量检查
  → E43F710(queue, packet) 入队候选调用
CD89F00：事件循环 → D789490(queue) 取包
  → 接口及上下文检查
  → CD8AF90(packet)：头、校验和、TLV、邻居缓存
  → CDAB1A0(packet)：遍历另外一组 registry 回调
  → 释放报文
```

`CD894C0` 检查 task ID 状态后，通过 `D792920` 传入名称、入口、栈参数等。结合之前对创建器的复核，这里是 IOS 内部 task；这不证明存在一个同名 Linux pthread，也不能把传入的整数直接解释为 Linux 调度优先级。

`CD89F00` 调用 `D73DDF0(65, CD8AB90)`。本轮还复核了这个包装器：普通分支最终向 `D717190` 传入 registry `3814B3D8`。**65 是这个登记接口中的键**，不能因此叫它 IP 协议号。底层所有入包路径如何消费此 registry，仍待补齐。

接收回调 `CD8AB90` 检查报文所带接口对象、接口相关状态、全局启用值以及队列容量。部分拒绝路径释放报文，另一些路径交给通用处理函数。队列成功接收与协议字段解析发生在不同函数中，查丢包时应分别看这两层。

`CD8AF90` 的普通分支明确存在以下行为：

- 检查至少 4 字节的 CDP 头，以及版本值 1/2。
- 计算并检查校验和值；失败有独立统计与诊断路径。
- 按大端 type/length 遍历 TLV，检查长度至少为 4、长度不超过剩余空间。
- 检查 Device ID，查找或分配邻居记录，调用 `CD97B10` 进行后续缓存插入/更新。
- 使用头中 TTL 字节设置计时，并更新接收统计。
- 部分 TLV 和后处理通过 registry 间接回调扩展，尚未枚举全部消费者。

这说明当前主 ELF 内确实包含这一段 CDP 检查与状态处理实现。它不证明驱动、平台入包或每一个扩展 TLV 都在同一个 ELF 中。

一个反例尤其有用：init 登记的 `CD9AE70` 会遍历邻居桶并按接口移除记录，属于清理路径。它虽然是 CDP 初始化时登记的回调，也不能当成收包入口。

## BGP：消息类型与会话状态一起决定处理

由接收日志引用进入 `EFCCF10`，可看到消息类型分支、KEEPALIVE、UPDATE、NOTIFICATION、未知类型及同步错误等路径。它是已经有具体实现证据的消息处理函数，不能仅依据 subsystem 名称替代这一层分析。

普通分支的类型 1 分支调用 `EFCFCE0`；类型 2 分支在满足内部会话状态判断时调用 `F20A5E0`。不满足相关状态时存在明确的 `rcvd UPDATE - not in ESTABLISHED state` 路径。这里的类型解释同时由分支代码与周围消息处理支持；内部状态的所有枚举值及 UPDATE 属性解析仍未完整恢复。

`F12F8F0` 内调用 `EFCCF10(a1, 0x32, 1)`，并包含会话关闭和邻居状态处理；另一个直接调用者是 `EFE4980`。这些调用给出了继续向上查调度与输入来源的入口。TCP 字节流如何组装到这层、部分缓冲对象的生命周期、全部属性处理和 RIB 更新边界仍待追踪。

不要把 `CF95270(179, F138190)` 直接画成“TCP/179 → BGP 消息解析”。本轮复核 `F138190` 看到的是查找对端及复制字符串一类行为；这个 registry 键的消费语义仍未证明。端口数字、回调指针和协议名同时出现，也不足以证明数据流。

## OSPF：协议输入分发后，还有队列与消息分发

`FBE9060` 从对象的两个队列取包，取得 IP 头长度及后续消息位置，更新统计，再按消息类型调用不同处理函数。类型 4 调用 `FC05800`，类型 5 调用 `FC04E90`，类型 3 调用 `FBF0600`，类型 2 调用 `FBF16F0`。

在 `FC05800` 中可见 LS Update/LSA 处理、MaxAge 诊断以及对邻居和数据库相关函数的调用。`FBE9060 → FC05800` 是本轮核对过的局部调用关系；它还不是从设备入包点到 LSDB 的完整链。前面的认证、接口/区域选择、排队入口和各类 LSA 的完整校验仍有缺口。

init 中的 `CF3FA80(89)` 仅把一个字节值追加到小表，并清零对应计数，不能当成“登记了 OSPF 报文解析回调”。另一个 init 回调 `FC71740` 处理接口相关对象及状态，也不是本轮找到的 LS Update 入口。

## CLI：新增三类语法动作的解释

新解码位于 `grammar_semantics.py`，路径解释位于 `syntax_paths.py`。普通 CLI 与 simulation 分支分开处理，不执行目标回调。

| 动作 / 消费函数 RVA | 恢复内容 | 保留内容 |
|---|---|---|
| `generic_prefix_action` / `E3A5E90` | 有符号 16 位地址/前缀长度存储偏移、帮助指针、地址类型键、flags、`/` 分隔及前缀长度解析 | `3CB56200` 地址解析 registry、类型键对应的 family、回调、界限与上下文条件；显示为 `<prefix:dynamic>` |
| `deprecated_action` / `E38D8A0` | 将 parser context `+301C` 的逻辑值设为 1，然后仅走 accept，不消费输入 | 标记的下游用途；不能因此判定命令不可达 |
| `whitespace_action` / `E393260` | alternate、NVGEN 直接 accept、普通输入的空白/边界检查；不输出一个伪造的 CLI 单词 | 字符类别表、实际输入、上下文字段和消耗长度；NVGEN 未知时保留两种条件路径 |

`DEF4DC0` 在安排 accept 时临时推进 parser context `+2F5C` 的输入偏移，之后恢复。由此可解释为什么空白动作既不是无条件 epsilon，也不应成为命令关键字。边界检查使用位集合中的字符码 0、33、59，不能概括成“只检查空格”。

历史 config 未知清单中，三类动作分别出现 252、43、30 次，共 325 个节点。这是**节点数量，不是新增命令数**。本轮对每类选择 4 个节点，共 12 个，重新读取暂停进程中的 transition、动作分发表和必要描述符，核对消费函数后运行新解码器。prefix 例子出现类型键 1 和 20，但未根据数字猜测地址族。

旧未知清单及大图未被覆盖；325 个历史节点没有全部在新会话重读，也没有据此重新计算整条命令路径覆盖率。

新的 `linkage` 入口复用有类型的链表解码器。本轮两批共取得 48 条 dynamic linkage 记录、37 条 pending binding 记录；两条链都还保留续读位置。第二批先读小状态，再读链表，避免长链耗尽预算而使状态一直读不到。读到的 `service internal enabled` 与 `first-enable helper attempted` 均为 0。

这只支持“这些具体链表记录和状态在该暂停时段被观察到”。pending 不等于隐藏，dynamic 不等于所有相关条件已放行。完整列表、完整命令图与可执行性要分别验证。

状态查询的模块枚举达到 512 条上限，缺口被保留。单次读取和链表采集也不宣称原子快照；没有自动暂停、继续或执行 CLI。大型 IDB 保存不会在每次小时检查中重复触发。

## 从这些实现理解设计取向

**观察事实**：多个功能通过 subsystem init 安装 registry 回调，部分输入先进入队列，再由内部 task 处理；CLI 用共享 parser context 和描述符驱动，不同参数类型还可以通过另一个 registry 扩展。

**设计解释（推断）**：这种组织允许大量功能复用接收分发、调度和解析设施，同时按平台、接口与运行状态接入实现。它也解释了为什么“一个巨大的 ELF”里仍有很多可分开的功能边界，为什么静态调用图不足以表示运行时流程。

这个解释不等于已恢复源码中的全部抽象。要回答某个协议“由谁处理”，应给出所处阶段、登记与消费证据、队列或任务边界、字段及错误处理、外部边界和未知项。主 ELF 中见到解析函数可以确认该局部实现；确认 so 或另一个进程的职责，仍须实际绑定、消费端或 IPC 接收证据。
